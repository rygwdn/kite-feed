Open-source llm-d 1.0 adds controls for production AI inference

Category: AI

Contributors to llm-d, an open-source system for distributing large language model inference across computing clusters, released version 1.0 on Oct. 20 at the PyTorch Conference North America. The project, governed by the Cloud Native Computing Foundation (CNCF), adds controls for sharing infrastructure among users, upgrading services without interruption and routing multi-step AI-agent requests to servers that retain reusable context [1][2][16]. The release targets operating and computing costs as agents generate repeated bursts of requests. In a separate benchmark, IBM and Red Hat said llm-d served up to 3,000 coding agents on 544 Nvidia H100 GPUs, with peak output above 6.6 million tokens per minute. They estimated the cost per token was one-fifth to one-tenth of equivalent commercial API pricing [7][1]. The companies reported those results from demonstrations. The software is available as open source, and Google Cloud said it is integrating it into Google Kubernetes Engine [13][2].

Key Points

  • Cache reuse: IBM Research reported a prefix-cache hit rate of approximately 98% and a blended serving cost of about $0.11 per million tokens in a quantum error-correction research workload [1][3].
  • Google test: Google reported that cache-aware routing and host-memory offloading on its Ironwood TPU cut median time to first token by more than 85% and increased throughput to 2.4 times that of a standard Kubernetes service [2].
  • Flow controls: The version 1.0 router can queue and prioritize requests by workload and tenant. It retains first-come, first-served scheduling unless operators enable new policies [10][9].
  • Current adoption: DigitalOcean uses its own llm-d fork for Managed Agents and Serverless Inference, while JetBrains runs the framework behind its Junie Lite plan [12][4].

Perspectives

DigitalOcean: Salman Paracha, senior vice president of AI engineering, said distributed serving is essential to scaling the company's GPU fleet and improving cache reuse. He cautioned that software components optimized for different chip architectures are not readily interchangeable today [12].

Moor Insights & Strategy analyst Jason Andersen said llm-d could help extend the useful life of older GPUs as performance gains from newer generations eventually slow. He warned that vendor support does not necessarily amount to a firm commitment to the project [12].

Technical Details

  • Disaggregated serving: The system separates prompt processing (prefill) and token generation (decode) into distinct pools. It coordinates updates to both as one logical unit so traffic can be routed to compatible versions [2][7].
  • Tiered KV cache: When accelerator memory fills, llm-d integrations can move cached context to host memory and then to storage, preserving reusable state for later requests rather than immediately evicting it [2].
  • Priority scheduling: The router maintains separate request queues by tenant and priority, dispatches higher-priority work first and cycles fairly among tenants within a priority band. A probabilistic admission controller can shed excess load [10][7].

Industry Impact

  • Cloud inference: Google Cloud says its GKE Inference Gateway runs the llm-d router. The project reports that a separate production integration reduced time to first token by more than 35% and doubled the prefix-cache hit rate from 35% to 70% in Vertex AI [10].
  • GPU utilization: Google says scheduling asynchronous inference during idle reinforcement-learning cycles can raise aggregate accelerator duty cycles from about 40% to above 70% [2].
  • Cloud providers: The project describes deployments on AWS and Oracle Cloud Infrastructure, including AWS-reported gains of up to 70% in tokens per second compared with standard vLLM on SageMaker HyperPod [10].

Historical Background

Red Hat said its team initially focused on vLLM, an open-source inference server, as open-weight models spread. It then found that enterprise users needed cluster-level orchestration to coordinate model serving across infrastructure [16][6].

Q&A

Q: Which reliability feature is still planned rather than included in version 1.0?

A: Active-active routing and failover for individual inference requests remain planned; version 1.0 provides a standby router and high availability [9].
