Researchers demonstrate PHP attack bypassing a key server defense

Category: Technology

Cybersecurity firm VulnCheck has developed an exploit that bypasses Address Space Layout Randomization (ASLR), a defense previously considered a major obstacle to exploiting PHP’s PHP2Shell flaw on real-world x86-64 servers [22]. The two PHP vulnerabilities can let attackers run code remotely without authentication, and VulnCheck’s demonstration bypasses a widely used server protection [19][22]. VulnCheck has restricted access to the exploit to its paying intelligence customers [22]. The PHP Foundation says cybersecurity contractor Chainguard violated an agreed embargo, after which details began circulating and the project moved its patch release forward [59]. Cloud providers and security researchers have also reported probes before public disclosure [24][35]. PHP is also bundled into services and third-party products. Updating a content-management system or its plugins alone does not necessarily fix the underlying PHP runtime, and security vendors are still assessing products that bundle it [8][21]. Cogent Security reported that, by 8 p.m. ET Wednesday, fewer than 1% of affected assets it tracked had been patched [4].

Key Points

  • Cloudflare’s Matthew Prince said the company saw thousands of exploit attempts in the 10 hours before public disclosure, tens of thousands within 45 minutes afterward, hundreds of thousands within two hours, and millions by the time of his post [4].

Perspectives

PHP Foundation: The foundation called the prolonged delay in resolving the out-of-memory flaw a structural failure, citing a consensus-driven decision process and a shortage of developers with deep engine expertise. It said it would move to majority decisions and encourage compromises [23].

Red Hat: Red Hat rated the vulnerabilities less severely than the National Vulnerability Database did. It said reliable exploitation of one requires precise heap manipulation and timing, and that remote code execution is difficult in practice and typically depends on non-default behavior [21].

Timeline

  • 2024: PHP developers identified early signs of the out-of-memory issue [59]
  • 17 October 2026: Amazon detected an attempt to exploit PHP2Shell against its MadPot honeypot [19]
  • 20 October 2026: PHP vulnerability identifiers began circulating online before scheduled disclosure [59]
  • 21 October 2026: PHP issued emergency fixes a day ahead of planned disclosure [21]
  • 22 October 2026: VulnCheck reported an exploit bypassing ASLR on x86-64 servers [22]

Technical Details

  • VulnCheck's demonstration targeted CVE-2026-109618, an out-of-memory corruption flaw that can lead to remote code execution [22].
  • Exploit traces: CrowdStrike said exploitation can leave worker processes stable and return normal HTTP 200 responses, with no application code recorded. It identified a memory-limit fatal error in the web server error log as the only server-side trace [19].

Industry Impact

  • Software and cloud vendors: Cisco was reviewing more than 30 products and cloud services; AWS was addressing exposure in Elastic Beanstalk, WorkMail, Amazon Linux and Lightsail, while Google Cloud updated supported PHP runtimes in App Engine [21].
  • Legacy deployments: Cisco Talos estimated that about half of PHP systems may not receive a patch and urged operators using PHP 8.1 or earlier to move to a supported release [21].

Historical Background

The PHP Foundation said it had known about the underlying out-of-memory issue since 2024, but researchers had not yet found a concrete route to remote code execution [59][23]. An external security audit helped identify the problem, and AI-assisted research later clarified how attackers could exploit it [59][23].

Q&A

Q: What should operators do if they cannot secure an affected system promptly?

A: U.S. cybersecurity agencies urged organizations to disconnect affected systems that cannot be secured promptly [8].

Action Items

  • Check for PHP bundled into services and products: Inventory server images, hosting components and third-party products rather than checking only websites that explicitly advertise PHP. Update the runtime itself because content-management system or plugin updates may not address the underlying flaw [8][60].
